# Features

This page links each current product feature to its stakeholders, goals, requirements, user flows, implementation paths, planned acceptance coverage, status, and risk. It only describes behavior found in the current repository.

## ID Policy

Stable IDs use the exact prefix, hyphen, and three digit shape from `docs/wiki/01-index.md` and `docs/wiki/02-governance.md`: `STK-001`, `GOAL-001`, `REQ-001`, `UC-001`, and `FEAT-001`. Source files and planned test notes don't receive stable IDs on this page.

Legacy `UC01`, `UC02`, `UC03`, `UC04`, `UC12`, `UC13`, `UC14`, and `UC15` names remain aliases only. Each alias maps one to one to the canonical `UC-0xx` value recorded in `docs/wiki/03-product.md`. This page uses canonical IDs in the table.

## Proposed CMS 운영 콘텐츠 관리 Capability

Status: `Proposed`, unnumbered candidate. This is not a current implementation, not an approved product feature, and not a new stable ID.

Evidence: `.omo/evidence/cms-content-authority-baseline.json` records that the proposed CMS is not current implementation, the public static SPA has no runtime auth or RBAC, target edits are docs only, and the current stable feature set remains `FEAT-001` through `FEAT-010`.

Trigger: Operators need a reviewable way to manage content sources that now feed the static public app through bundled data, config, i18n copy, and media paths. The trigger is operational content authority, not a runtime app behavior change.

Managed resource categories:

1. `센터 카탈로그`, center names, regions, addresses, descriptions, affiliate flags, optional detail fields, map place data, SNS, parking, prices, and center images as content records.
2. `운영 이벤트·정기모임`, event banner and regular meeting content that affects existing event and meeting presentation.
3. `다국어 콘텐츠`, Korean and English UI copy plus localized center and operational content.
4. `미디어 자산`, image files, placeholders, alt text, and publication checks for public media used by center cards and details.
5. `공통 운영·외부 연동 설정`, shared departure, Instagram, Naver Map place data, and other operational settings that affect public links or banners.
6. `게시·검증 메타데이터`, draft state, publisher identity after CMS authentication, validation results, publish time, rollback pointer, and evidence for content release checks.

Affected existing concepts/IDs: `STK-003`, `GOAL-005`, `REQ-003`, `REQ-006`, `REQ-011`, `REQ-014`, `REQ-016`, `REQ-017`, `REQ-018`, `REQ-019`, `REQ-020`, `UC-014`, `UC-015`, and existing features `FEAT-001` through `FEAT-010` may be affected if this candidate is later promoted. This section does not change their current behavior, status, acceptance notes, or code paths.

Non-goal: This proposal does not add CMS implementation, public app login, public app RBAC for visitors, source data edits, schema changes, package changes, or acceptance criteria for a new feature.

Change note, 2026-09-16: The Project owner decided to pursue a Supabase-based backend with Supabase-managed authentication/authorization for operators. This supersedes the "backend services" and "runtime data fetching" items that were previously listed as non-goals here; the Supabase shape, RLS, and auth design now live in `docs/wiki/05-architecture.md` (Supabase backend) and `docs/wiki/07-reference/02-data-schema.md` (Supabase table contracts), tracked as `docs/wiki/09-decisions.md` `WIKI-DEC-005`. Every other non-goal in this list still holds, including public app login/RBAC for visitors, which stays scoped to operators only.

Update, 2026-09-17: The data store and public read path are implemented (`docs/wiki/05-architecture.md` Supabase backend, items 1-2, 6). `FEAT-001` through `FEAT-010` code paths were updated in the table above to point at `src/contexts/DataContext.jsx`/`src/lib/supabaseClient.js` instead of the JSON files; behavior and acceptance criteria are unchanged. The public app still has no runtime auth or RBAC for visitors; operator authentication exists in Supabase but no app UI exercises it yet (Phase 1 uses Supabase Studio directly).

Owner-decision requirement: The Product Owner must approve the content model, authorization policy, promotion from proposal to implementation scope, any stable ID creation, and any change to existing product scope or current feature behavior. CMS authorization is separate from public app behavior. An authenticated content publisher may independently publish after CMS authentication only if the Product Owner approves that CMS policy.

No stable ID: This proposed capability has no `FEAT-011`, no new `REQ`, no new `UC`, and no other stable ID. It stays outside implementation authority until owner approval promotes the model, policy, stable ID, and scope changes.
